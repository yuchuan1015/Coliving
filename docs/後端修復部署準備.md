## 備份、migration 022 與發布順序

以下步驟是未來發布的順序，**本輪未執行**。

1. **固定兩份候選來源。** 後端與前端各自用獨立 worktree，保存最終 commit、套件版本、測試結果及發布檔案雜湊。後端包只含本次程式與必要 migration，不帶本機 DB、`.env`、`.venv` 或測試資料。前端先完成 build；不能在正式 main 目錄中順手重建前端。
2. **核對當前版本與復原材料。** 在不輸出密鑰內容的方式下，確認上表的正式服務／路徑、可用容量及原啟停狀態；保存前端完整 dist、後端程式清單、完整 venv 及正式設定備份。若正式來源有本地未版控修補，先保存並比對，不可直接覆蓋。需要同時容納主 DB、照片、記憶、舊環境與候選套件的備份；空間不足先處理，不半途換包。
3. **停止所有寫入來源。** 進入維護窗口，先停止已確認的 scheduler timer，等待正在執行的 scheduler 完成，再停止兩個 MCP，最後停止 API。API 含背景 mem0 daemon thread，停止前應避開新聊天／寫記憶並等已有請求及背景作業結束；repo 沒有背景作業持久佇列或可靠的排空指標，不能承諾強制終止不遺失剛排入的記憶。核對相關程序已退出、DB／Qdrant 無持有者，再開始一致性備份。
4. **建立一致的資料備份。** 主 DB 使用 SQLite backup API 產生可獨立開啟的副本；同一停寫窗口保存私人照片、uploads、Qdrant 目錄、mem0 history 與 SDK 目錄。不要只複製正在写入的 `.db` 而漏掉 WAL，也不要啟動第二個 Qdrant client 讀正式向量庫來備份。為所有備份建立 SHA-256 清單；副本做 `PRAGMA integrity_check`，確認是 `ok`，並檢查 tar／檔案清單完整。備份要可讀回，不能只看指令 exit 0。
5. **先在副本驗證 migration。** 022 只做 `ALTER TABLE users ADD COLUMN auth_version INTEGER NOT NULL DEFAULT 0`；可重跑，不删除資料。用候選 Python 對主 DB 的額外演練副本連跑兩次，確認欄位、非空、預設值及原有資料／各表筆數未變；演練不啟動應用、不連供應商、不執行 scheduler。
6. **套用程式與套件，再遷移正式 DB。** 三個服務保持停止，把核定候選套件裝入已備份的正式環境，`pip check` 通過；以明確的後端檔案清單發布，排除所有資料與設定目錄，不使用整棵 repo 的 `rsync --delete`。對確認存在的正式主 DB 執行候選的 `migrations/022_auth_version.py`，再驗 `integrity_check`、欄位及筆數。022 不會一次執行舊的 001–021；如果正式 schema 與交接前提不符，停下釐清，不把整包 migration 猜著跑完。
7. **啟動 API，再啟動兩個 MCP。** API startup 也會補 `auth_version`，但不能拿這個便利機制取代備份與明確遷移。先確認 API 正常、資料路徑沒飄到空目錄，再啟動公開及私人 MCP；所有服務須是同一份候選程式。重連舊 MCP 客戶端，不能只看 unit 是 active。檢查無 import error、SQLite 欄位錯誤或 Qdrant lock 錯誤。
8. **驗後端，再切前端。** 先完成下節驗收，再按既有發布紀錄完整備份 dist，資產先上傳、保留舊雜湊資產／預覽，校驗候選與當前入口 hash 後各自原子替換 `index.html`、`sw.js`，公開前端目錄／檔案沿用 755。沒有全套多檔原子交易，故必須保持新舊資產都可取得。驗新介面、MIME 和資產 hash，再按原設定恢復 scheduler timer 並觀察下一次執行；不要為驗收手動執行會向住戶送 webhook 的 `wake_scheduler.py`。

SQLite 備份可用下面的獨立小程式；路徑參數必須由發布前核對結果填入。它不匯入鴉巢、也不讀 `.env`。`BACKUP` 必須是不存在的新路徑，且所在目錄已設為只有部署人員可讀。已用暫存假資料驗證備份內容、完整性、檔案權限、拒絕覆蓋及拒絕不存在的來源；**尚未對正式 DB 執行**：

```python
# 用法：python sqlite_backup.py SOURCE BACKUP
import os
import sqlite3
import sys
from pathlib import Path

os.umask(0o077)
source, target = map(Path, sys.argv[1:3])
if not source.is_file() or target.exists():
    raise SystemExit("來源必須存在，備份目的地必須是新檔")
with sqlite3.connect(source.resolve().as_uri() + "?mode=ro", uri=True) as src:
    with sqlite3.connect(target) as dst:
        src.backup(dst)
        if dst.execute("PRAGMA integrity_check").fetchall() != [("ok",)]:
            raise SystemExit("備份完整性檢查失敗，保留現場且不要繼續發布")
```

## 上線驗收與不能代替的檢查

先以公開、不寫資料的診斷確認 `/api/health`、未登入 `/api/users/me`、公開 MCP 的無憑證 challenge、私人 MCP 無憑證拒絕，以及 OAuth discovery。這只能證明路由和認證入口存在，不能證明使用者權限或 provider 工具迴圈可用。

完整驗收須使用已安排的測試帳號及測試內容，不能擅用住戶帳號、閱讀真私密內容或寄出訊息：

- 取得一次登入的 access／refresh，改密碼後確認兩者都拒絕；舊密碼不能登入，新密碼可登入。再改一次，確認上一版 token 仍無法恢復。前端成功後清掉憑證並顯示重新登入提示；其他尚開的頁面不能保留可讀的受限全文。
- 改住戶顯示名稱，確認只更新本人、失敗時草稿仍在；室友名稱是另一項產品行為，不能拿來替代本測試。
- 公開固定 MCP、OAuth MCP、私人 MCP 各自重連；正常測試帳號可讀自己的資料，已停用帳號不可用。作廢測試鑰匙和授權仍被拒絕。不要用同一個公開 MCP 成功結果包辦三種接法。
- 私密抽屜 ID 從 REST 拒絕、室友自己的 MCP 可讀；MCP 寫入僅一筆且回成功。記憶寫入、搜尋、超過 20 筆列表與跨室友刪除隔離須用測試內容確認，不能使用真住戶資料做探測。
- 親密中心至少兩頁測試文章，確認跨頁無重複、分類／分級在伺服器篩選、權限失效後列表和已開全文都撤下；退稿後原文章與審核資料一致。
- 真實 Gemini／DeepSeek 工具迴圈、mem0 各 provider 成功呼叫要另外使用核定的測試金鑰及用量。既有自動測試隔離了模型與 embedding，不能因此寫「正式五家模型全部驗收」。沒有測試金鑰就把此項標為未驗，不能借住戶金鑰試。

驗收紀錄只保存測試名稱、版本、狀態碼、計數及結果；不保存密碼、完整 token、金鑰、私人全文或含 token 的 URL。

## 回復策略：保留撤銷語意與新資料

**migration 022 是加欄位，不代表本輪可無條件整包退回。** `auth_version` 是持久的撤銷狀態。住戶改密碼後，舊 token 仍可能沒有到期；如果換回不檢查 `ver` 的舊 `get_current_user`／refresh 路由，即使 DB 留著新欄位，被撤銷的 token 也會再次通過。只隱藏前端改密碼按鈕不能修正這個問題。

1. **只有前端出問題：** 確認沒有較新的發布後，恢復本次部署前的前端入口與資產，繼續使用已修復後端及現行 DB。舊介面可忽略新增 API 欄位。已改密碼的人仍用新密碼登入，旧 token 仍拒絕；不要為前端問題還原 DB。
2. **後端新功能出問題，但 DB 可用：** 優先修復前進，或只撤回有問題的非認證／非隱私改動。維持現行資料、`auth_version`、新密碼雜湊，以及這一輪的私密內容與停用帳號保護。若要用舊功能版本，必須先製作並測試保留安全修復的候選包；至少保留 `User.auth_version`、access／refresh 生成與驗證、登入／刷新傳遞版本、改密碼的版本增加及其測試。不能只保留驗證器，卻把登入改回一律簽 `ver=0`。回復前後都驗「先登入 → 改密碼 → 舊 access／refresh 拒絕」；相關修正散在模型、schemas、services、routers、deps，不能盲目用單一檔案清單覆蓋。
3. **候選包尚未對外放行即啟動失敗：** 若已證明期間沒有任何新寫入、舊程序／timer 都停止，資料副本可以用於修復本次遷移事故；但重新公開的程式仍應保留安全修復。不要重新開放交接前已確認有抽屜與記憶權限漏洞的整包舊後端。沒有通過測試的候選包時保持維護，不承諾一鍵回復。
4. **對外放行後需要恢復資料：** 先保留故障時刻的完整現況副本，停止寫入。不能直接以部署前 DB 蓋回：這會丟失新帳號／內容、恢復旧密碼，以及讓已作廢的 MCP keys／OAuth grants 復活。若資料可讀，先以現況修復；若不得不還原，需另做依穩定 user ID 對應的資料復原方案，保存最新密碼雜湊、單調不減的 `auth_version`、帳號停用、MCP 作廢及 OAuth 撤銷狀態，同時處理停寫前新增的帳號與內容，並與照片／向量／記憶歷史使用一致時點。無法取回这些最新狀態時，不能公開還原副本；須先完成另案的帳號與連線復原流程，不能假定部署前备份等於安全狀態。

**不要以更換 `JWT_SECRET` 當作快速登出／回復辦法。** `services/crypto_service.py` 用它衍生 Fernet 金鑰解密住戶 API key；它也用來簽 MCP／OAuth token、照片連結與推導私訊碼。直接改值除了切斷連線，還會使現存加密 API key 無法解密。真正的金鑰輪替要有舊密鑰可用時的重新加密與憑證遷移，本輪沒有準備或授權這項作業。

復原完成後保留 `auth_version` 欄位，不執行向下遷移、不歸零。完成回復驗證後才恢復 timer 及對外存取，記錄實際保留／回復的版本與資料時點。
